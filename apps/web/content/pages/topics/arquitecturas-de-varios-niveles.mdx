La arquitectura de varios niveles (de tres niveles, de n niveles) es un patrón que se usa desde hace décadas y que sigue siendo muy común en aplicaciones orientadas a usuarios. Divide la aplicación en capas separadas por la red, de modo que cada una se pueda desarrollar, operar y escalar por su cuenta. En el examen aparece tanto en su forma clásica, con servidores, como en su versión sin servidor.

## Qué problema resuelve

Cuando toda la aplicación vive en un mismo bloque, cualquier cambio o fallo en una parte afecta al resto, y no puedes escalar solo lo que está saturado. El patrón de varios niveles ofrece un marco general para que los componentes estén desacoplados y escalen de forma independiente, y para que se puedan desarrollar, administrar y mantener por separado, a menudo por equipos distintos.

## Conceptos clave

### Los tres niveles

Aunque el vocabulario varía, una aplicación de varios niveles suele tener estos componentes:

- **Nivel de presentación**: lo que el usuario usa directamente, como páginas web o la interfaz de una aplicación móvil.
- **Nivel de lógica**: el código que convierte las acciones del usuario en funcionalidad, por ejemplo operaciones de lectura y escritura en la base de datos o procesamiento de datos.
- **Nivel de datos**: los medios de almacenamiento que guardan los datos de la aplicación, como bases de datos, almacenes de objetos, cachés y sistemas de archivos.

La arquitectura de tres niveles, con un único nivel de cada tipo, es la implementación más popular, pero el patrón se puede aplicar mucho más allá de una aplicación web típica.

### La red como frontera entre niveles

En este patrón, un nivel tiene que hacer una llamada de red para hablar con otro. Por eso construir una aplicación de varios niveles suele exigir piezas repetitivas que cambian poco de una aplicación a otra: código que define una cola de mensajes para comunicar niveles, código que define una API y un modelo de datos, y código de seguridad que controla el acceso.

Una buena práctica del pilar de fiabilidad de AWS Well-Architected señala como antipatrón invocar API directamente entre niveles sin capacidad de conmutación por error ni de procesamiento asíncrono de la solicitud. Las colas, los flujos de trabajo y los balanceadores de carga son dependencias débilmente acopladas que ayudan a aislar el fallo de un componente.

### Versión con servidores en una VPC

La guía de Amazon VPC describe dos ejemplos para producción que ilustran cómo se separan los niveles en la red:

- **Servidores web y de base de datos**: una VPC con subredes públicas y privadas en dos zonas de disponibilidad. Los servidores web reciben el tráfico de los clientes a través de un balanceador de carga, y los servidores de base de datos se ejecutan en las subredes privadas. Los grupos de seguridad se encadenan: el de los servidores web acepta tráfico del balanceador de carga y el de la base de datos acepta tráfico de los servidores web.
- **Servidores en subredes privadas con NAT**: los servidores se ejecutan en subredes privadas de dos zonas de disponibilidad, los lanza y termina un grupo de Auto Scaling y reciben las solicitudes a través de un Application Load Balancer. Salen a internet mediante un NAT gateway, que se despliega en ambas zonas de disponibilidad para mejorar la resiliencia.

Desplegar en varias zonas de disponibilidad con Amazon EC2 Auto Scaling permite mantener la capacidad mínima que necesita la aplicación, y el balanceador de carga reparte el tráfico entre las instancias del grupo.

### Versión sin servidor

AWS ofrece servicios para crear aplicaciones de varios niveles sin administrar servidores:

- **Nivel de lógica**: Amazon API Gateway y AWS Lambda. API Gateway permite iniciar funciones de Lambda directamente mediante solicitudes HTTPS, y ambos servicios escalan automáticamente según el volumen de solicitudes. Con Lambda no eliges, proteges, parcheas ni administras un sistema operativo, ni dimensionas servidores. API Gateway simplifica el despliegue, la supervisión y la protección de las API, y puede mejorar su rendimiento con caché.
- **Nivel de presentación**: cualquier cliente capaz de usar HTTPS puede llamar a la API, así que este nivel puede ser una aplicación de escritorio, una aplicación móvil, una página web o un dispositivo IoT. Amazon S3 con Amazon CloudFront sirve sitios estáticos, como aplicaciones de una sola página, sin aprovisionar un servidor web. Amazon Cognito añade registro, inicio de sesión y control de acceso, y AWS Amplify ofrece alojamiento administrado para aplicaciones web estáticas.
- **Nivel de datos**: usar Lambda en el nivel de lógica no limita el almacenamiento. Las funciones se conectan a cualquier almacén incluyendo el controlador de base de datos adecuado, y usan acceso basado en roles de IAM o credenciales cifradas con AWS KMS o AWS Secrets Manager. Hay opciones sin servidor, como Amazon DynamoDB o Amazon Aurora, y otras que no lo son.

### Varios niveles frente a otras arquitecturas

Diseñar según los requisitos implica saber cuándo usar este patrón y cuándo otro:

- **Varios niveles**: separa la aplicación por capas técnicas (presentación, aplicación y datos). Sigue siendo un patrón popular para aplicaciones orientadas a usuarios.
- **Microservicios**: separan la funcionalidad en verticales cohesivas según el dominio de negocio, en lugar de por capas técnicas. Cada servicio es una unidad independiente y sin estado que se comunica con las demás.
- **Basada en eventos**: los componentes se comunican emitiendo y respondiendo a eventos, normalmente de forma asíncrona, lo que añade latencia variable a cambio de escalabilidad y desacoplamiento.

Los tres patrones se combinan: un nivel de lógica puede estar formado por microservicios que se comunican mediante eventos.
